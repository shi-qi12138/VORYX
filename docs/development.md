# 功能开发与维护规范

当前能力、交付边界和已验证环境由进度看板和环境报告维护。 [开发进度](project-status.md) · [环境报告](environment.md)

## 1. 开发入口

先从 [功能规格](requirements.md) 找到功能 ID。新增功能使用 [功能设计模板](templates/feature.md) 写清用户场景、模块归属、接口与验收，再修改实现。

改接口前检查 [接口契约](api-reference.md)；改依赖前检查 [架构](architecture.md)。如果实现暴露设计问题，先修订契约并记录变更，再同步调用点和示例。

文件布局遵守 [目录规范](repository-layout.md)，C++ 排版遵守现有根 .clang-format，代码组织与完整括号遵守 [代码规范](code-style.md)。控制语句即使单行也不省略 {}，空格与换行不自行压缩。

## 2. 一个功能的完整流程

1. 明确输入、成功结果、失败结果与不属于本次交付的范围。
2. 画出依赖变化，说明哪些模块拥有对象，哪些只借用。
3. 补齐参数、默认值、边界、线程、生命周期和状态变化。
4. 列出三后端映射；不能实现的能力明确拒绝，不添加无效果的成功分支。
5. 按 [自动化测试方案](automated-testing.md) 为真正的失败风险设计测试，复用公共后端一致性用例；实现阶段将相应测试纳入 CTest。
6. 实现最小完整流程；不预建无用途的管理器、继承层或全局对象。
7. 同步 API、教程、功能状态和变更记录，运行受影响验证。
8. 保存环境与结果，按验收条件完成后才标记“已实现”。
9. 在开发日记追加日期、成果、验证和遗留事项，更新进度看板；职责、源码归属或构建目标发生变化时同步模块说明。 [开发日记](development-log.md) · [开发进度](project-status.md) · [模块说明](module-map.md)

## 3. 模块与 CMake 规则

- 每个模块只包含自己的私有目录和声明的公共依赖，禁止仓库根目录作为万能 include 路径。
- 后端 SDK 与系统链接库使用 PRIVATE；公共 API 不要求用户安装未启用后端的 SDK。
- Runtime 是后端工厂的组装位置。RHI、Renderer 不反向调用 Runtime。
- 不以全局变量保存设备、当前窗口、当前命令列表或 Renderer。
- 后端之间不包含头文件。共享实现提取前须证明行为与生命周期一致。
- 公共接口 target 与后端实现 target 分离，防止链接依赖形成环。
- 开发时用仓库共享的 CMake 预设，接入 SDK 时按需显式启用后端。 [构建命令与开关](environment.md)
- 两平台构建和 WSI 开关按 [跨平台规范](cross-platform.md) 执行；Windows/Linux 都验证公共层和 CPU/Null，DX12 仅 Windows，Linux X11/Wayland 分别测试。
- 禁止以绝对盘符、大小写容错或 Windows 系统类型实现通用代码；平台系统头只进入相应私有适配。

## 4. C++ 规则

- 公共命名空间使用 voryx；类型使用 PascalCase，函数使用 PascalCase，字段使用 lowerCamelCase。
- 所有权用类型表达；主要使用 unique_ptr 和值对象，借用使用引用或明确的非拥有指针。
- 多态接口有虚析构；析构函数不得抛异常。普通业务对象优先组合，继承仅用于契约实现。
- 不在 public API 中暴露 Vulkan、D3D12 或 OpenGL 类型。
- 所有 public API 要求完整头文件依赖；不能依赖用户先包含另一个头文件。
- 默认值写入接口契约；不得用未初始化字段表达“自动”。
- 字节数和偏移显式标注，计算做溢出与范围检查；外部输入错误不能仅靠 assert 处理。
- Result 错误不得丢弃；底层原始错误码与公共类别一并保留诊断。
- 不强制所有对象使用 PImpl 或虚接口；抽象要有明确的替换或封装目的。
- 统一构建配置内使用 C++ 类型，不宣传跨编译器 ABI 稳定性。

## 5. 增加后端

1. 新建独立后端 target，私有包含 SDK；实现公共 RHI 契约。
2. 通过设备探测填充能力表；不支持的格式、模式或特性返回 Unsupported。
3. 向 Runtime 显式注册工厂，分别处理“未编译”和“创建失败”。
4. 实现命令状态、资源依赖、完成标记、帧取消与设备丢失路径。
5. 运行公共一致性样例和验证工具，记录硬件、驱动和构建配置。
6. 只有这些检查通过后，才能在支持矩阵中标记可用。

不为接入某后端在 Renderer 中增加 BackendType 分支。差异应由后端适配，或通过明确的能力和可选扩展表达。

## 6. 改接口与版本

草案阶段可以修订，但仍需记录旧行为、新行为、原因、受影响教程及测试。冻结后删除字段、改变默认值、改变所有权、改变线程要求、改变错误恢复方式都视为兼容性变更。

发布版本的破坏性改动须提供迁移说明；弃用项标明替代方案与移除版本。不仅依据函数签名判断兼容性。

每次接口变更应在一个变更集中同步：接口文档、实现、样例、测试、功能表和 [变更记录](changelog.md)。禁止仅更新声明后留文档到以后补。

## 7. 完成标准

- 功能 ID 与验收条件可追踪，所有已支持后端均有结果，未测环境明确标记。
- 正常、边界、失败与清理路径有适当验证；验证范围与风险匹配。
- 用户能找到实际可编译的示例和错误恢复说明；设计阶段示例始终标明状态。
- 没有新增循环依赖、公共 SDK 泄漏、全局隐式依赖或未说明的数据持有。
- 新接口说明返回是否代表 CPU 接收、GPU 提交还是 GPU 完成。
- 尚未验证的性能、支持范围或兼容性不能写成已满足。
- 格式、完整括号与适用的自动化测试通过；零测试、缺少必需依赖或必需 GPU 用例被跳过不能作为通过。
